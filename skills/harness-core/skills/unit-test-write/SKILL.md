# 单元测试编写技能（unit-test-write）— {{LANGUAGE}} 版

> **流水线阶段**: ③ 第三步
> **输入**: `status: testing` 的 change.md + ② 交付的实现与核心失败测试
> **出口门禁**: 全部 AC/边界/降级有测试 · `{{TEST_CMD}}` 通过 · `{{LINT_CMD}}` 零新增告警 · 核心覆盖率 ≥80%
> **测试框架**: {{TEST_FRAMEWORK}}

### 核心规则（一句话摘要）

> **核验每条 AC 至少一个测试（② 已有则保留），补齐每条边界与每条降级路径，核心覆盖率 ≥80%。禁止只测 happy path。**

---

## 1. 职责

你在 **② 之后** 补测试缺口。失败测试先行已在 `coding-skill` 完成，本阶段不要退回重写实现、不要无故推倒 ② 的核心测试。

本阶段要做：核验核心 AC 测试仍锁行为且仍绿；补边界、降级、回归；把覆盖率拉到核心逻辑 ≥80%。目标不是为覆盖率而测，而是验证每条 AC、每个边界、每条降级路径真实成立。

---

## 2. 前置检查

1. **定位目标 change**（按 `.harness/rules/变更定位规则.md`）：
   - 扫描 `.harness/changes/*/change.md`，过滤 `status: testing`
   - 用户已指定 `<id>` → 校验该 change 状态是否为 `testing`，否则报错
   - 恰好 1 个 → 自动选中
   - 0 个 → 报错：无处于 `testing` 状态的 change，退回 ② coding-skill
   - ≥ 2 个 → **列出候选清单（id + 标题 + 摘要），停下请用户选择**，不得擅自默认取第一个
2. 核对 ② 交付物：核心 AC 失败测试仍在且能跑；change.md 里标给 ③ 的边界/降级未测项作为本阶段清单
3. 缺前置 → 退回 ② coding-skill

---

## 3. 工作流程

### Step 1: 梳理测试矩阵
从 `change.md` 提取所有 AC、边界、降级（及 ② 标明交 ③ 的项）。若走迭代协议：用 `test/design.md` 取验证策略，建立「测试点 → 测试用例」映射，**TC 写入并对账** `.harness/iterations/<id>/test/cases.md`（每条 AC 至少 1 个 TC、无孤立 TC）。

### Step 2: 分层测试
| 层级 | 内容 |
|------|------|
| Spec Tests | **核验** ② 留下的每条 AC 核心行为测试仍绿、仍锁行为；缺口才补，禁止无故重写 |
| Boundary Tests | 空/零值、极值、并发、重复执行；**性质类**（若该 AC 适用）：对称/交换律（排序、归一化、拼接等**必测反序输入**）、幂等性（一次性关闭/开关重入/重复执行）、往返一致性（编码↔解码、归一↔解析） |
| Failure/Fallback Tests | 依赖故障时的降级逻辑（超时/限频/API 不可用）——本阶段必补 |
| Regression Tests | 已修复 bug / 历史故障回归 |

### Step 3: 编写测试
- 命名: `{{TEST_NAMING}}`
- 用 {{TEST_FRAMEWORK}} + {{MOCK_LIB}}，断言用 {{ASSERT_LIB}}
- 每个测试**单一断言意图**，Arrange-Act-Assert 三段清晰
- **降级逻辑必须实测**，不满足于"应该能处理"

### Step 4: Mock 原则
- Mock 外部依赖（LLM、第三方 API、数据库、缓存）
- **禁止 Mock 自己写的业务类**（那样测的是 Mock 不是逻辑）
- 用 {{MOCK_LIB}} 提供可控的故障场景（超时、异常、空返回）

### Step 5: 覆盖率核验
- 跑 `{{COV_CMD}}`，核心逻辑 ≥80%（看报告阈值，不是把覆盖率命令本身当成「全绿」）
- 覆盖率不足 → 补测试，而非降低标准
- 纯 getter/setter/配置类可豁免

### Step 5.5: 阶段出口全量门禁复核

对**当前完整工作区**重跑（含本阶段新增测试文件；禁止只拿 ② 的 V6 结论）：

- `{{LINT_CMD}}`（本 change 涉及范围）相对进入本 change 前**零新增**告警；为空则跳过并在 change.md 注明。测试文件里的死代码/自赋值等由本次 lint 兜住。⑤ `unit-test-ci` 仍会再跑全量静态检查，此处不是流水线最后一道
- `{{TEST_CMD}}` 全绿；`{{RACE_DETECT_ARG}}` 非空则带上做竞态检测，为空则跳过并在 change.md 注明「本地未跑竞态」
- `{{FORMAT_CHECK_CMD}}` 通过；为空则跳过
- `{{COV_CMD}}` 报告核心逻辑 ≥80%

### Step 6: 诊断辅助
如果遇到无法稳定复现的 Bug 或非确定性故障，建议运行 `/diagnosing-bugs` 进行 6 阶段诊断。
诊断结果记录到 `.harness/changes/<id>/diagnosis.md`。

---

## 4. 测试质量红线

- ❌ 只测 happy path，边界靠注释"应该能处理"
- ❌ 断言空泛（只判断 true/非空，不锁具体行为）
- ❌ 测试间相互依赖、有顺序耦合
- ❌ Mock 自己写的类
- ❌ 无故删除或重写 ② 已转绿的核心 AC 测试
- ✅ 每条 AC 至少一个测试（可复用 ②）
- ✅ 每个边界情况至少一个测试
- ✅ 降级逻辑有专门测试

---

## 5. 完成标志

同时满足以下才允许 `testing → reviewing`，进入 ④ 专家评审：

1. ✅ 每条 AC、每条边界、每条降级路径均有对应测试（迭代协议则 `test/cases.md` 已对账）
2. ✅ `{{TEST_CMD}}`（及非空的 `{{RACE_DETECT_ARG}}`）通过
3. ✅ `{{LINT_CMD}}`（涉及范围，含新增测试文件）零新增告警；`{{FORMAT_CHECK_CMD}}` 通过（空命令跳过）
4. ✅ `{{COV_CMD}}` 显示核心逻辑覆盖率 ≥80%
