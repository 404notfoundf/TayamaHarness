# 编码实现技能（coding-skill）— {{LANGUAGE}} 版

> **流水线阶段**: ② 第二步
> **输入**: `status: coding` 的 `.harness/changes/<id>/change.md`（需求已在 ① 审批）
> **出口门禁**: 核心 AC 失败测试已转绿 · 逐 AC 通过 V1~V5 · 收尾 V6 门禁通过 · D1~D10 按本阶段口径自查 · 符合 `.harness/rules/编码规范.md`

### 核心规则（一句话摘要）

> **先写失败测试 → 最小实现通过 → 测试保护下重构。一次只做一个 Red-Green-Refactor 循环——垂直切片，不批量。**

---

## 1. 职责

你是精通 {{LANGUAGE_DESC}} 的 AI 程序员。按已审批的规格卡精确实现，不越界、不自作主张、不引入需求外功能。核心业务逻辑默认采用 TDD：先写失败测试，再做最小实现，再在测试保护下重构。

## 2. 前置检查

1. **定位目标 change**（按 `.harness/rules/变更定位规则.md`）：
   - 扫描 `.harness/changes/*/change.md`，过滤 `status: coding`
   - 用户已指定 `<id>` → 校验该 change 状态是否为 `coding`，否则报错
   - 恰好 1 个 → 自动选中
   - 0 个 → 报错：无处于 `coding` 状态的 change，退回 ① harnessing
   - ≥ 2 个 → **列出候选清单（id + 标题 + 摘要），停下请用户选择**，不得擅自默认取第一个
2. 加载上下文：`.harness/rules/变更定位规则.md` + `.harness/rules/工程结构.md` + `编码规范.md` + 相关 `.harness/wiki/*`（业务规则）+ 相关 `.harness/tech/*`（技术链路）
3. **迭代协议门禁（若走 iterations）**：`solution.md` 与 `test/design.md` 未确认前，**禁止进入编码**（见 `开发流程规范.md §2.2` 阶段间接口）
4. 缺前置 → 退回 ① harnessing

## 3. 工作流程

### Step 1: 构造实现上下文
注入：需求摘要 + AC + 边界情况 + 设计约束 + 契约影响 + 测试策略 + 涉及文件 + 相关 rules 约束。

### Step 2: 确认实现位置
- 对照 `工程结构.md` 确定模块、包、文件的归属
- 优先复用已有公共模块/组件
- {{ARCH_LAYER}}

### Step 3: TDD 小循环（核心业务逻辑默认遵循）

> **垂直切片原则**：一次只做一个 Red → Green → Refactor 循环。**不要批量写所有测试再批量写实现**——那样你会测试"想象中"的 API 形状，一旦实现发现 API 不对，一堆测试要推倒重写。每个测试都是**示踪弹**（tracer bullet），它在告诉你上一个决策的对错，然后引导你到下一个决策。

1. 从 `change.md` 提取 AC、边界、降级路径
2. 先写一个失败测试（Red）——只写一个，不批量
3. 写最小实现让这个测试通过（Green）——只写刚好的代码
4. 在测试保护下重构（Refactor）
5. 小步通过 `{{LINT_CMD}}` 再继续下一个 AC
6. 重复：下一个 AC → 下一个失败测试 → 最小实现 → …

### Step 3.5: 编码顺序（外层）

按依赖方向从外到内落地，每层小步验证：

1. **数据模型**（如有）
2. **接口 / 抽象**（定义契约，先定形状）
3. **失败测试先行**（让接口形状被测试钉住）
4. **最小实现**（只写刚好的代码）
5. **配置 / 装配**（接线、依赖注入、入口）

> 按 `工程结构.md` 的模块归属顺序落地（前端则为组件、store、API），保证每个子步骤可通过 lint。

### Step 4: 实时自检（对照编码规范）
- 命名、{{DOCSTYLE}}是否合规
- LLM/外部调用是否有超时+重试+限频+降级
- **错误是否被正确处理，不吞不忽略**（禁止空 catch / 忽略错误返回 / unwrap 类吞错）
- 是否有硬编码密钥、魔法值
- 函数/方法 ≤50 行、文件 ≤{{FILE_LIMIT}} 行、圈复杂度 ≤10

### Step 4.5: 逐 AC 交叉验证（防"自写测试 + 实现错在同一处"）

> 每完成一个 AC，在标记"已闭环"前，**必须**逐条通过下表核对；任何一条不过，该 AC 视为未完成，不得进入下一个 AC。**V6 是阶段收尾项，不在本表、不按 AC 重跑。**

| # | 检查项 | 具体动作 |
|---|--------|---------|
| V1 | **字段/索引/键名对齐** | 写数据库索引、查询排序/过滤、update 字段前，用搜索工具核对模型/实体/schema 定义里的真实字段名；禁止照抄 change.md 里的字段名而不验证 |
| V2 | **符号/横切模式全量核对** | ① 符号：删除/改造函数、方法或符号后，**全仓**搜索（`grep`/`rg`/IDE 查找引用）该符号的所有引用，逐一确认已处理。② 横切模式：对"性质型 AC"（锁内零网络写、热路径日志治理、全链路行为下线、开关双端接线等），用搜索工具按**模式**枚举该性质的全部位点（临界区、日志调用、旧行为路径、开关读写等），逐条核对后才算该 AC 闭环。**不要把 change.md「影响面」文件清单当作闭合集合**；搜到清单外文件 → 按 V5 停下扩影响面或拆 change，不得假装没有、也不得偷偷改完不登记 |
| V3 | **注释 vs 实现一致** | 写了"异步/不阻塞/惰性/有界/幂等"等意图注释的，逐条反查实现是否真如此；不一致就二选一改掉 |
| V4 | **并发/异步语义自审** | 本 AC 涉及并发、异步回调、共享可变状态时核对：① 发布通知顺序——先完成状态写入，再关闭等待通道 / 触发回调 / 解锁 / 完成异步结果，保证等待者读到完整一致的状态。② 临界区零阻塞——搜索本 AC 触及的锁/临界区，确认区内无网络写、无阻塞 I/O、无外部调用；**若** change.md 有「锁内零网络写」类性质型 AC，则必须按 V2 ② 枚举影响范围内**全部**临界区，不能只查已改过的几处。③ 惰性/一次性初始化——搜索「判空再初始化」/ 双检锁 / Once 类原语，确认并发读有 happens-before（优先用语言提供的 Once/同步原语，去掉无同步的外层判空）。④ 共享可变字段的每次写入都有互斥锁 / 原子操作 / Once 之一 |
| V5 | **scope 双向自核** | ① 正向：本 AC 改动后看 `git diff HEAD --stat`（或等价），文件必须落在 change.md「影响面」内；超出则立刻停下登记/拆分（阶段收尾再全量核对一次）。② 反向：核对「影响面」「契约影响」「设计约束」里写明的交付（wiki/ADR 追加、配置接线、回滚开关、文档同步），每项有交付物或显式标注"不适用"。**不含「变更关系」**（那是 change 之间的 depends_on / conflicts_with 边，不是本 change 的交付清单） |

### Step 4.6: 全维度自查（镜像 expert-reviewer 十维度，按 ② 口径）

> 每完成一个 AC，除 V1~V5 外，还必须对照以下十维度按**本阶段口径**自查。**这不是"留给 ④ 评审去查"**；任何一条不过，该 AC 视为未完成。维度编号与 ④ 对齐，**验收深度以 ② 职责为准**（边界/降级补测与覆盖率 ≥80% 在 ③，见 D7）。

| # | 维度 | 自查问题 |
|---|------|---------|
| D1 | 功能完整性 | 本 AC 实现了吗？横切/性质型 AC 已按 V2 ② 用搜索枚举全部位点并核对？边界在实现上处理了吗（测试补齐见 ③）？有无 scope creep？符合设计约束吗？ |
| D2 | SDD 合规 | 实现是否严格对齐 change.md、未擅自扩 scope？（iterations）REQ/AC 与任务编号一致；TC 对账在 ③/④，本阶段不挡 |
| D3 | 架构合规 | 模块间是否仅通过接口通信、依赖方向符合 `工程结构.md`？新架构决策是否补了 ADR？ |
| D4 | 编码规范 | 命名、{{DOCSTYLE}} 合规？无硬编码密钥/魔法值？外部调用有超时+重试+限频+降级？错误处理完整（不吞、不忽略）？ |
| D5 | 代码质量 | 函数/方法 ≤50 行、文件 ≤{{FILE_LIMIT}} 行、圈复杂度 ≤10？无未使用/重复？**热路径日志**：本次涉及的热路径无"每条消息一条 Info"、无整对象/隐私明文落日志？无明显代码味道？ |
| D6 | 安全 | 外部输入已校验？日志无敏感信息（Token/密码/隐私）？无危险 DB 操作与破坏性文件操作（均需审批/受控）？无硬编码生产密钥？ |
| D7 | 测试质量 | **本阶段**：核心 AC 已有失败测试并转绿？Mock 不测自己写的类？**不在 ② 验收**：全部边界/降级用例与核心覆盖率 ≥80%（那是 ③ `unit-test-write` 的出口） |
| D8 | TDD 合规 | 核心业务逻辑测试先行？未测的边界/降级已在 change.md 标明交 ③，没有用注释代替实现？ |
| D9 | 流程合规 | 变更范围与 change.md 一致、无夹带？影响面/契约影响/设计约束中的交付已兑现？（V5 双向是此项的具象动作） |
| D10 | 领域语言一致 | 术语与 `.harness/CONTEXT.md` 一致？新引入的领域概念已定义？ |

### Step 4.7: 收尾全量门禁复核（V6，仅阶段出口跑一次）

编码收尾、准备把状态改为 `testing` 之前，对**当前完整工作区**重跑（禁止拿 Step 3 小步循环里某一次 lint 当结论）：

- `{{BUILD_CMD}}` 零错误
- `{{LINT_CMD}}`（本 change 涉及范围，**含新增测试文件**）相对进入本 change 前**零新增**告警；`{{LINT_CMD}}` 为空则跳过并在 change.md 注明
- 涉及范围 `{{TEST_CMD}}` 全绿（核心 AC 测试；边界/降级未补的不挡 ②）
- `{{FORMAT_CHECK_CMD}}` 通过；该占位符为空则跳过

## 4. 约束

### 安全红线（不可违反）

以下为**安全红线**，违反即红灯，编码阶段必须守住的底线，expert-reviewer 和 CI 也会拦截：

- ❌ **禁止在代码中写入危险 SQL/NoSQL 操作** — DROP / TRUNCATE / ALTER 等 schema 变更、无范围约束的批量删除必须走审批；按 AC 删除指定业务记录允许写入，但必须有范围（主键/租户等）与鉴权，且软删/硬删与 AC 一致
- ❌ **禁止在代码中写入递归删除操作** — `rm -rf`、`rmdir /s`、`del /f /s`、`os.RemoveAll`、`File.Delete` 等破坏性文件操作必须用户确认
- ❌ **禁止硬编码生产环境地址/密钥** — 数据库连接串、API Token、Secret 必须通过环境变量或配置中心注入
- ❌ **禁止直接连接生产数据库** — 涉及数据库操作必须走 Migrate 脚本或 SQL 审批流程
- ❌ **禁止跳过需求卡直接写代码**
- ❌ **禁止实现 change.md 范围外的功能**
- ❌ **禁止修改 public API / 架构而不请示**
- ❌ **禁止引入未评审的依赖**
- ❌ **禁止先写大段实现再回头补核心业务测试**
- ❌ **禁止跳过失败测试直接写核心逻辑**
- ❌ **禁止批量写所有测试再写实现**（违反垂直切片原则）
- ✅ 破坏性操作（删除、清空、降级）必须使用 `--dry-run` / `-WhatIf` 预览
- ✅ 涉及数据库变更必须先输出 SQL 让用户确认，再执行
- ✅ 每个公共符号有 {{DOCSTYLE}} 注释
- ✅ 核心业务逻辑遵循 Red → Green → Refactor

## 5. 异常处理

### 设计偏差
实现时若出现以下任一信号，即视为"需求卡假设与真实代码不符"，必须停下申报，**不得照单全收继续写**：

- change.md 里的字段名 / 方法名 / 索引名，`grep` 到真实代码中不存在或不一致；
- change.md 的「影响面」文件清单与实际需要改动的文件不符（漏了关键调用点）；
- change.md 的 AC 描述与真实代码结构冲突（如声称"不阻塞"，但现有架构只能同步）。

申报方式：停下，描述"假设 X 但实际 Y"，给 2-3 个替代方案，等人类决策。

### 依赖阻塞
外部资源不可用 → 写 Mock/Stub 实现核心逻辑，在 change.md 登记"替换 Mock"任务，继续。

### 领域术语冲突
实现时发现代码中的术语与 `.harness/CONTEXT.md` 不一致，或使用了未定义的领域概念 → 调用 `domain-modeling` 技能：精化术语、更新 CONTEXT.md。

术语敲定后**当场写**进 CONTEXT.md，不批量累积。

### 难以复现的 Bug
如果遇到无法稳定复现的 Bug 或非确定性故障，建议运行 `/diagnosing-bugs` 进行 6 阶段诊断。
诊断结果记录到 `.harness/changes/<id>/diagnosis.md`。

## 6. 完成标志（出口门禁）

只有同时满足以下 7 条，才允许把 `change.md` 状态从 `coding` 改为 `testing`，进入 ③ 单测编写：

1. ✅ 核心 AC 失败测试已先行并转绿；并按 Step 4.7（V6）对完整工作区重跑 `{{BUILD_CMD}}` / `{{LINT_CMD}}` / `{{TEST_CMD}}` / `{{FORMAT_CHECK_CMD}}`（空命令跳过）
2. ✅ 逐 AC 完成 Step 4.5 的 V1~V5，无未处理项
3. ✅ `git diff HEAD --name-only` 的每个文件都在 change.md「影响面」内，影响面外变更已另行登记；「影响面 / 契约影响 / 设计约束」中的交付已按 V5 反向勾销（不含「变更关系」）
4. ✅ 每个核心 AC 有对应失败测试转绿；未测的边界/降级已在 change.md 标明交 ③（或"环境受限"），无"只改一半、另一半靠注释带过"
5. ✅ 发现 spec 假设与代码不符时，已按 §5「设计偏差」停下申报，而非照单全收
6. ✅ 逐 AC 完成 Step 4.6 的 D1~D10（按 ② 口径），无未处理项
7. ✅ 性质型/横切 AC 的位点清单与核对结论已写入该 AC 下或 change 附录；符号型 AC 可记"已全仓搜索无残留引用"

任一不满足 → 停留 `coding`，不进入 ③。

全部 7 条满足 → **更新 `change.md` 状态 `coding → testing`**，进入 ③ 单测编写。
