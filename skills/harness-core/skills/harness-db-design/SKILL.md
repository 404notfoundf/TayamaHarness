# Harness DB Design — 数据库设计

从 `.harness/changes/<id>/change.md` 的需求与验收标准，产出**数据模型设计**：实体 → 表结构 → 索引 → 约束 → 迁移脚本，并把设计沉淀到 `.harness/wiki/数据模型.md` 与迁移文件。

> **定位**: 与 `database-migration-toolkit` 分工——本技能负责**设计**（表结构/关系/索引该长什么样），`database-migration-toolkit` 负责**执行**（把设计落地为可回滚的迁移脚本并执行）。设计定稿后优先交 toolkit 按项目 Flyway/Liquibase 规范落地；若项目尚无迁移目录，可暂写 SQL 草案，但表名/列名须与 wiki 一致。

---

## 1. 何时使用

- change 新增/修改业务实体、关联关系、状态流转、字段
- 涉及索引、唯一约束、外键、级联策略
- 需要评估存量表迁移（加字段/改类型/拆表/归档）

> **时机**：涉及库表/持久化的 change，宜在 **`coding` 之前**完成本技能；`status` 为 `analyzing` 时设计，`coding` 前须已定稿 wiki。

## 2. 前置

1. 按 `.harness/rules/变更定位规则.md` 定位目标 change（`status: analyzing` 或 `coding`）。
2. 加载 `.harness/rules/数据库命名规范.md`——表/列/索引命名；若存在 `.harness/rules/ORM与库表映射.md`（语言包注入）一并加载。
3. 加载 `.harness/wiki/数据模型.md`（若存在）——理解**存量模型**，新设计必须与之兼容（存量风格优先于默认单数表名等）。
4. 加载 `.harness/CONTEXT.md`（若存在）——列名/表名须与统一语言一致；缺术语时先更新 CONTEXT 或走 `domain-modeling`。
5. 读取 `change.md` 的「验收标准」「边界情况」「契约影响 · 数据模型」。
6. 确认目标数据库类型与迁移工具（MySQL + Flyway 等），与项目现有 `migrations/` 布局一致。

## 3. 执行流程

### Step 1: 识别实体
从 AC 与用户故事提取实体（名词），确定实体间关系（1:1 / 1:N / M:N）与基数。

### Step 2: 表结构设计

**命名**：表/列/索引按 `数据库命名规范.md`；应用层字段对照按 `ORM与库表映射.md`（若有）+ wiki「ORM 映射」表。与存量 wiki 冲突时以**存量 wiki 风格**为准并在变更记录说明。填表时「说明」列须写 CONTEXT 术语。

对每个实体输出：

| 字段 | 类型 | 约束（PK/FK/UNIQUE/NOT NULL） | 默认 | 说明 |
|------|------|-------------------------------|------|------|
| id | <DB 主键类型> | PK | auto | 主键 |
| <字段> | <类型> | <约束> | <默认> | <说明（CONTEXT 术语）> |

**结构与类型（设计决策，命名规范管名字不管类型）**：

- **主键策略**：自增 / 雪花 / UUID 择一（按项目约定），禁止业务字段作主键
- **索引**：覆盖 change/AC 中的查询与排序路径；组合索引最左前缀；极小表除外，避免无索引全表扫
- **约束**：业务不变式优先 UNIQUE/CHECK；外键按项目约定（常见：逻辑外键 + 应用层校验）
- **金额**：定点类型（如 `DECIMAL`），禁止 `FLOAT`/`DOUBLE` 存钱；单位写 wiki 说明列
- **JSON / 大段扩展**：类型与结构在 wiki 说明（或链 SCHEMA）；列名仍走命名规范，避免无说明的 `data`/`info`
- **ORM**：在 wiki 填写库列 ↔ 应用层字段对照，并符合 `ORM与库表映射.md`（若有）

### Step 3: 变更评估（对存量表）
若改动存量表，列出**兼容性清单**：

| 存量表 | 变更类型（加字段/改类型/拆表/归档） | 是否破坏性 | 迁移策略 |
|--------|----------------------------------|-----------|---------|
| <表> | <变更> | 🟢 兼容 / 🔴 破坏 | <先加字段后回填 / 新表+切换+删旧> |

**铁律**：破坏性变更（删列/改类型/改约束）必须先评审、可回滚、避开高峰，禁止直接 `DROP`。

### Step 4: 落盘
1. 更新 `.harness/wiki/数据模型.md`：erDiagram + 表结构 + 变更记录 +（可选）ORM 映射表。
2. 调用 `database-migration-toolkit` 落地迁移（推荐）：输入须含与 wiki **逐字一致**的表名/列名/索引名；脚本命名遵循项目 Flyway/Liquibase 约定（如 `V<c>__C-0NN_<desc>.sql` 与配套回滚）。
3. 在 `change.md` 的「契约影响 · 数据模型」补充本次模型变更摘要。
4. 若发现 CONTEXT 缺术语或命名冲突，先更新 CONTEXT / `domain-modeling`，再定稿列名与迁移。

## 4. 自检清单

- [ ] 每个实体有明确主键，索引覆盖查询路径
- [ ] 表名/列名/索引名符合 `数据库命名规范.md`，与存量 wiki 无同义异名
- [ ] 每个新列在 CONTEXT 或 wiki 说明中有术语依据；无未登记缩写
- [ ] 库列与应用层字段对照已写入 wiki，且符合 `ORM与库表映射.md`（若有）
- [ ] 无破坏性变更未标注/未评审
- [ ] 迁移脚本含回滚，或已交 `database-migration-toolkit` 且与 wiki 列名一致
- [ ] `数据模型.md` 已同步，无"代码改完了文档还是旧的"
