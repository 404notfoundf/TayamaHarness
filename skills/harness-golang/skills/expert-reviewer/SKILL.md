# 专家评审技能（expert-reviewer）— Go 版

> **流水线阶段**: ④ 第四步
> **出口门禁**: 0 个 🔴 严重问题

### 核心规则（一句话摘要）

> **不手下留情。逐项审查 change.md 完整性、架构、编码、安全、测试、流程合规。0 个 🔴 才放行。**

---

## 1. 审查维度与清单

### 维度 1: 功能完整性（对照 change.md）
- [ ] 实现了 **所有** AC？
- [ ] 处理了 **所有** 边界情况？

### 维度 2: 架构合规（对照 工程结构.md）
- [ ] 依赖方向正确（common → models → rpc → api）？
- [ ] 服务间仅通过 RPC 通信？
- [ ] 新架构决策是否补了 ADR？

### 维度 3: 编码规范（对照 编码规范.md）
- [ ] 命名、注释合规？
- [ ] 无硬编码密钥 / 魔法值？
- [ ] LLM/外部调用有超时+重试+限频+降级？
- [ ] error 处理完整（不忽略、不吞）？

### 维度 4: 代码质量
- [ ] 函数 ≤50 行 / 文件 ≤800 行 / 圈复杂度 ≤10？
- [ ] 无未使用 import/变量（`go vet` 通过）？
- [ ] 无重复代码块？

### 维度 5: 安全
- [ ] 外部输入已校验？
- [ ] 日志无敏感信息？
- [ ] 竞态条件已检查（`go test -race`）？

### 维度 6: 测试质量
- [ ] 覆盖所有 AC 与边界？
- [ ] 测了降级逻辑？
- [ ] 核心覆盖率 ≥80%？
- [ ] Mock 合理（不 Mock 自己写的类）？

---

### 架构审查建议
如果评审发现架构层面的摩擦信号（浅模块、耦合过深、接缝缺失、测试困难），建议运行 `/arch-review` 进行深入架构体检。
