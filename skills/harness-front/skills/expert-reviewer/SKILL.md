# 专家评审技能（expert-reviewer）— 前端版

> **流水线阶段**: ④ 第四步
> **输入**: 代码 + 单元测试
> **产出**: `.harness/changes/<id>/review.md`
> **出口门禁**: 0 个 🔴 严重问题

### 核心规则（一句话摘要）

> **不手下留情。逐项审查 change.md 完整性、架构合规、编码规范、代码质量、安全、测试质量、流程合规、SDD/TDD 合规。0 个 🔴 才放行。**

---

## 1. 审查维度与清单

### 维度 1: change.md 完整性
- [ ] 用户故事与 AC 明确
- [ ] 边界情况 ≥3 个
- [ ] 设计约束已记录

### 维度 2: 架构合规
- [ ] 组件/模块放在正确的位置（对照 `工程结构.md`）
- [ ] 依赖方向正确（无循环依赖）
- [ ] 没有引入不必要的新依赖

### 维度 3: 编码规范
- [ ] 命名合规（PascalCase 组件、camelCase 变量）
- [ ] TypeScript 严格模式（无 `any`）
- [ ] 模板简洁（无复杂表达式、`v-for` 有 key）
- [ ] 样式隔离（scoped / CSS Modules）

### 维度 4: 代码质量
- [ ] 函数/组件 ≤ 规定行数
- [ ] 无重复代码
- [ ] 错误处理完整（loading/empty/error 三态）
- [ ] 无残留 `console.log` / `debugger` / TODO

### 维度 5: 安全
- [ ] 无 `v-html` 或已做 XSS 防护
- [ ] Token 存储合规
- [ ] 外部输入已校验

### 维度 6: 测试质量
- [ ] 覆盖所有 AC 与边界
- [ ] 测了降级/错误逻辑
- [ ] 核心覆盖率 ≥80%
- [ ] Mock 合理（不 Mock 自己写的逻辑）

### 维度 7: 流程合规
- [ ] 变更范围与 change.md 一致
- [ ] 无"偷偷"夹带的额外变更

### 维度 8: SDD 合规
- [ ] `change.md` 是否足够构成规格真相源
- [ ] 实现是否严格对齐 change.md，而非擅自扩 scope

### 维度 9: TDD 合规
- [ ] 核心业务逻辑是否体现测试先行
- [ ] 测试是否覆盖 AC / 边界 / 降级路径

## 2. 输出格式（写入 review.md）

```markdown
# 📋 评审报告

## 总览
- 审查文件: N 个
- 🔴 严重问题: N（必须修复）
- 🟡 建议改进: N（推荐修复）
- 🟢 通过项: N

## 🔴 严重问题
### 1. <标题>
- 文件: `<路径>:<行号>`
- 问题: <描述>
- 违反: <规范条目>
- 修复建议: <可操作方案>

## 结论
<一句话结论>

### 架构审查建议
如果评审发现架构层面的摩擦信号（浅模块、耦合过深、接缝缺失、测试困难），建议运行 `/arch-review` 进行深入架构体检。
```

---

## 3. 严重程度标准

| 级别 | 定义 | 示例 |
|------|------|------|
| 🔴 严重 | 功能异常 / 安全漏洞 / 架构腐化 | 模块间直接调用内部方法 |
| 🟡 建议 | 不立即出错但影响可维护/性能 | 组件过长、缺 JSDoc、TDD 痕迹不足 |

---

## 4. 完成标志

0 个 🔴 → 更新 `change.md` 状态 `reviewing → ci`，进入 ⑤ CI 门禁。
有 🔴 → 退回 ② 编码实现修复。
