# 共性能力与业务实践的协同边界

> 什么能力应该"统一沉淀、复用"，什么应该"留在业务侧、各自维护"？
> 本文讨论公共能力与领域项目 Harness 的边界，以及让两者协同的关键机制。

## 边界划分

| 层 | 内容 | 归属 |
|----|------|------|
| **共性能力** | 已验证的通用 Harness、流程 Skill、参考实现、数据协议、质量基线 | 统一沉淀，跨团队复用 |
| **业务实践** | 领域业务规则、项目内链路知识、项目规则 | 各团队的项目 Harness 保留 |

判断标准：**这条知识/能力换了业务团队还成立吗？** 成立 → 共性能力；只对本业务成立 → 留在项目 Harness。

## 让两者协同的三件套

### 1. 参考实现 + 可组合能力

共性能力以"**可组合能力**"而非"**一次性方案**"的形式提供，用**参考实现**降低上手成本。业务侧按需组合，而不是整体照搬一个庞大的框架。

### 2. 数据协议

跨系统共享数据时，先定义**数据协议**（Schema、语义、约束），让消费方基于协议协同，而不是各自猜字段含义。

### 3. 质量基线

统一共识的质量底线（如测试门禁、评审标准、发布门禁），让不同团队用同一把尺子衡量交付。

## 与脚手架的关系

脚手架正是"共性能力"侧的实现，通过三层分离支撑协同：

| 机制 | 脚手架载体 |
|------|-----------|
| 共性能力不复制进项目 | `.harness/skill-dependencies.json`（声明来源 + 兼容版本） |
| 项目只保留业务编排 | `.harness/skills/`（领域 Skill） |
| 协议 / 能力 / 门禁分离 | `rules/`（协议）+ `skills/`（能力）+ `scripts/`（门禁） |
| 数据协议 / 质量基线 | `.harness/wiki/接口协议.md`、`数据模型.md`、`rules/` 门禁 |

**核心命题**：共性能力统一沉淀、声明式引用；业务实践留在项目 Harness，两者靠数据协议与质量基线对齐。
