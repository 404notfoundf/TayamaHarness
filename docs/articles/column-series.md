### 01 · 工程纪律即架构

### 04 · apply-harness：安装引擎的设计哲学

`skills/apply-harness/SKILL.md` 是整个项目中最庞大的文件（130KB），是脚手架的总装线。它负责：
- **Step 1**：检测语言/框架（6 种语言 × 111 个框架差异块）
- **Step 2**：构建参数表（三级继承：基础参数 → 框架差异块 → 用户覆盖）
- **Step 3**：渲染技能模板（10 个 core 模板 × 参数表 → 语言包技能）
- **Step 4**：注册技能到 `.harness/`
- **Step 5**：生成 Owner Agent 定义

**核心命题**：安装不是"复制文件"，而是"检测 → 参数化 → 渲染"的三步流程。

> ✅ 已发布：`column-10-apply-harness.md`

### 05 · 🆕 SDD-TDD 方法论：三层关系

Harness 的方法论根基——SDD（规格驱动开发）、TDD（测试驱动开发）、Harness（约束体系）三层关系：
```
SDD → 定义"做什么"，规格真相源是 change.md
  └─ TDD → 定义"怎么写对"，Red → Green → Refactor
       └─ Harness → 定义"怎么被约束、验证、留档、收口"
```
为什么先写规格再写代码？为什么 AC 必须先可测试？为什么 change.md 是真相源？

**核心命题**：不是 TDD 取代了瀑布模型，而是三层叠加形成了"瀑布式思考 + 敏捷式执行"的混合模型。

> ✅ 已发布：`column-51-sdd-tdd.md`

### 21 · 🆕 Change Management：变更状态机与依赖 DAG

`docs/change-management.md` 定义的完整变更状态机：
```
drafting → reviewing → approved → coding → testing → reviewing → ci → verifying → done
```
每个 change 对应 `.harness/changes/<id>/` 下的三个文件（change.md 规格卡、review.md 评审报告、verify.md 验证报告）。依赖 DAG 决定了 change 的执行顺序，状态机保证了流水线不可跳步。

**核心命题**：变更不是"文件变更"，而是"状态流转"——每个状态对应一个阶段的出口门禁。

> ✅ 已发布：`column-20-change-management.md`

### 22 · 🆕 Owner Agent：脚手架的灵魂

`docs/owner-agent.md` 定义的四大职责：
- **身份持有**：项目名称、技术栈、参数表
- **规则裁决**：5 条规则，每个阶段对照校验输出
- **流水线编排**：6 阶段调度者
- **上下文维护**：CONTEXT.md 共享语言机制，多轮对话术语一致

**核心命题**：Owner Agent 不是一份"自我介绍"，而是一门"宪法"——它不是被阅读的，是被执行的。

> ✅ 已发布：`column-52-owner-agent.md`

### 23 · 🆕 6 阶段流水线：从全局看闭环

`docs/6-stage-pipeline.md` 的全局视角——为什么这 6 个阶段恰好构成完整闭环？为什么顺序不可逆、不可跳步？阶段门禁的设计哲学，每个阶段输入/产出/门禁的对齐。

**核心命题**：6 阶段不是"6 个步骤的列表"，而是一个"输入 → 转换 → 门禁"的递归结构——每个阶段的输出都是下一个阶段的输入，门禁是唯一合法的"出口"。

> ✅ 已发布：`column-53-pipeline.md`
