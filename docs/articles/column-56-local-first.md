# 本地优先：Agent + 文件夹 + Git

> 为什么不做一套复杂平台，而是把项目所需信息放进同一个文件夹、用 Git 管理？
> 本文阐述"本地优先"原则及其边界。

## 核心原则

尽可能把项目需要的所有信息放进**同一个文件夹**，用 **Git** 管理：

- Coding Agent 天然能操作**文件系统**；
- Git 补上**版本、分支、评审、来源、回滚**；
- 不需要建设复杂平台和操作界面，所有操作通过 Agent 打开文件夹对话进行。

## 本地优先 ≠ 全存本地

稳定上下文与动态事实分而治之：

| 类别 | 去向 | 举例 |
|------|------|------|
| 稳定上下文 | 进 Git | 业务知识、项目规则、源代码、迭代文档 |
| 动态事实 | 留在权威系统，提供 MCP/CLI 给 Agent 实时查询 | 工作项状态、测试环境、日志、数据库、配置中心 |

两者在 Agent 执行时汇合，而非预先全量灌入。

## 为什么先做文件 Wiki

代码、文档、测试、索引可以进入**同一个 MR**，一起评审，合并后共享同一个版本——一次迭代同时更新功能和知识，减少"代码已变、文档停在旧版"的漂移。外部 RAG 平台或本体图谱作为主知识源，会拉长更新链路（同步→切片→萃取→索引→发布），增加知识与代码漂移的机会。

> 文件 Wiki、RAG、本体不是互斥方案：文件 Wiki 管**维护/评审/版本化**，RAG 管**检索**，本体管**表达实体与语义**。优先文件 Wiki，是因为知识更新路径最短。

## 与脚手架的关系

脚手架正是"本地优先"的产物：`.harness/` 目录随项目 Git 一起版本化，知识、规则、变更、验证证据同仓管理；动态事实通过 `动态事实来源.md` 声明的 MCP/CLI 实时接入。

**核心命题**：稳定上下文进 Git，动态事实留在它应该在的地方。
