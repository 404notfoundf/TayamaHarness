# 为什么先做文件 Wiki：文件 Wiki vs RAG vs 本体论

> 面对知识沉淀，常见路线有三条：文件 Wiki、RAG 检索、本体图谱。
> 本文说明各自的定位，以及为什么**先做文件 Wiki**。

## 三种路线的分工

| 路线 | 解决什么 | 短板 |
|------|---------|------|
| **文件 Wiki** | 知识的**维护、评审、版本化** | 检索靠相对路径 + 全文搜索，规模大后需辅助 |
| **RAG** | 大规模语料的**检索召回** | 不解决知识本身的组织与质量，易召回过时/冲突内容 |
| **本体论（图谱）** | 表达**实体与语义**关系 | 建模成本高、维护重，冷启动代价大 |

它们**不是互斥**的：文件 Wiki 管维护，RAG 管检索，本体管表达语义。

## 为什么先做文件 Wiki

1. **更新链路最短**：改一个知识文件 → 进同一个 MR → 评审 → 合并即生效。
2. **与代码同版本**：代码、文档、测试、索引在同一个版本里，减少"代码已变、文档停在旧版"的漂移。
3. **可评审、可追溯**：知识像代码一样 diff、review，事实来源（`source`）可追溯到一手材料。
4. **零平台依赖**：不建设复杂基础设施就能起步。

外部 RAG 平台或本体图谱作为主知识源，会把更新链路拉长（同步→切片→萃取→索引→发布），知识与代码漂移的机会随之增加。

## 与脚手架的关系

脚手架的知识库正是**文件 Wiki** 的落地：

- `.harness/wiki/`（业务知识）+ `.harness/tech/`（技术上下文），Markdown 文件，随项目 Git 版本化；
- 每个文件 frontmatter 带 `source`，正文用相对路径关联；
- 迭代归档（`archive.md`）时把确认知识回流 wiki/tech，实现知识飞轮；
- 后期可把 Git 中的 wiki 作为 RAG 的**可信语料源**，甚至导出为本体，但主知识源始终是文件。

**核心命题**：先文件 Wiki——它管维护，RAG 管检索，本体管语义；别在冷启动时先上最重的方案。
