# 真正的瓶颈是上下文，不是模型能力

> 模型能力在快速提升，但它进入一个真实业务系统后，仍会遭遇大量信息缺口。
> 本文论证：业务 AI 研发的上限，不只在模型，更在**上下文**。

## 信息缺口从哪来

模型不知道：

- 历史上**为什么**这样设计
- 某条规则**只适用于哪些业务**
- 某段代码是**当前链路**还是**已废弃实现**

## 靠人重述的代价

如果每次都在对话里重新讲解，AI 的表现就受制于**当前对话长度**和**个人表达能力**。同一个问题，换一次会话、换一个人、换一个 Agent，结果可能完全不同。

## 结论

```
模型决定通用能力，上下文决定它在具体项目中能走多远。
```

上下文不是提示词的附属品，而是需要**像代码一样被版本化、评审、维护**的资产。这正是脚手架把知识库（wiki/tech）纳入 `.harness/`、与代码同仓管理的原因——把"靠人每次重述"变成"靠仓库稳定供给"。

## 与脚手架的关系

| 上下文来源 | 脚手架载体 |
|-----------|-----------|
| 业务规则、口径、异常处理 | `.harness/wiki/`（frontmatter 带 `source`） |
| 跨系统链路、废弃状态、观测方式 | `.harness/tech/`（`wiki_ref` 反连业务知识） |
| 术语一致性 | `.harness/CONTEXT.md` |
| 动态事实（环境/日志/DB/工作项） | `.harness/动态事实来源.md`（MCP/CLI 实时查询） |

**核心命题**：稳定上下文进 Git，动态事实留在它应该在的地方——两者在 Agent 执行时汇合。
