# 第十六章 · 灵魂拷问：harness-me-golang 的设计哲学

> 苏格拉底说：教育不是灌输，而是点燃火焰。
> harness-me 做的是同一件事——不替你设计方案，而是用一连串问题，把你脑子里的模糊想法点燃成可执行的规格。
>
> —— 项目信条：**需求不是问出来的，是拷问出来的。**

---

## 一、为什么需要"拷问"？

### 1.1 需求的三种形态

任何需求在到达代码之前，都要经历三次变形：

| 形态 | 特征 | 问题 |
|------|------|------|
| 脑海中的想法 | 模糊、跳跃、充满假设 | 说不清楚 |
| 说出来的话 | 简化、丢失细节 | 表达失真 |
| 写下来的规格 | 结构化、可执行 | 往往漏掉边界 |

**人类大脑里的需求，从来不是完整的**——它是一堆相互矛盾的愿望、隐含的前提、未说的约束。而 AI 最常见的问题就是：**把第一句话当成完整需求**，然后一路狂奔。

### 1.2 AI 直接开工的三个灾难

如果一个 AI 拿到一句"帮我做个用户系统"就直接开写代码：

```
灾难①：范围失控 —— 聊天记录只有 3 分钟，代码却已经写了 3000 行
灾难②：假设错误 —— AI 假设了"注册要邮箱验证"，其实业务只要手机号
灾难③：返工地狱 —— 需求确认时发现完全做偏了，推倒重来
```

### 1.3 拷问的本质：让需求"显形"

harness-me 的核心洞察：**需求不是被 AI "猜"出来的，而是在对话中被"问"出来的。** 每次问答，都让一个模糊的假设显形，变成可验证的陈述。

```
   模糊想法             一次拷问              清晰规格
```

## 二、一次只问一个问题：为什么？

### 2.1 苏格拉底式的节奏

harness-me 的第一原则是**一次只问一个问题**。这不是效率低，而是认知科学的选择：

| 方式 | 效果 |
|------|------|
| 一次抛 10 个问题 | 用户懵了，只能挑好答的答，模糊地带全被跳过 |
| 一次问 1 个 | 用户完整思考，答案有质量，决策树才能延续 |

### 2.2 决策树推进

每个答案都会打开新的问题分支。拷问不是随机问，而是沿着决策树前进：

### 2.3 五层拷问模型

harness-me 的问题库分为五层，从外到内：

| 层 | 关注点 | 典型问题 |
|----|--------|---------|
| 第一层：需求边界 | 目标与范围 | "这个需求的核心目标是什么？一句话说清楚。" |
| 第二层：用户与场景 | 谁用、何时用 | "谁是最主要的用户？他们在什么场景下会用到？" |
| 第三层：功能细节 | 行为与交互 | "当用户输入 X 时，系统应该做什么？" |
| 第四层：设计约束 | 边界与限制 | "这个功能必须在什么约束下实现？性能、安全、合规？" |
| 第五层：风险与回退 | 失败与兜底 | "如果方案做到一半发现不可行，你的 Plan B 是什么？" |

**重要原则：不要做"问题展览"**——问题要按需挑选，顺着用户的答案走，而不是把问题库从头念到尾。

## 三、拷问的对话纪律

### 3.1 对话纪律一：不急着给答案

AI 的天性是"解决问题"。但 harness-me 要求：

> **你的任务是问更好的问题，而不是替用户想方案。**

一旦 AI 开始给方案，用户就会进入"评估模式"，停止深度思考。拷问的效果就消失了。

### 3.2 对话纪律二：一次一个问题

在用户回答完之前，不要抛第二个问题。可以追问其答案的具体化，但不另起炉灶。

```
✅ 好。那么"注册"是什么形式——邮箱、手机号、还是第三方登录？
❌ 那"注册"是什么形式？还有"登录"怎么做？要不要找回密码？验证码呢？……
```

### 3.3 对话纪律三：追着不确定点

用户回答里出现这些词，就是拷问的**信号词**：

| 信号词 | 危险 | 追问 |
|--------|------|------|
| "大概" | 模糊假设 | "具体是多少？有量化的目标吗？" |
| "应该" | 未经证实 | "这个假设成立吗？有依据吗？" |
| "可能" | 未定方向 | "哪个是主路径？哪个是备选？" |
| "简单点" | 被压缩的复杂度 | "简单到什么程度？哪些复杂度可以砍？" |
| "和以前一样" | 隐式参照 | "以前的具体行为是什么？有文档吗？" |

### 3.4 对话纪律四：一次拷问到够，然后收

拷问不是无限循环。当出现以下信号，应该收尾：

- 五个层面都已覆盖
- 每个"信号词"都被追问过
- 边界情况已经摸清（至少 3 个）
- 验收方式已经明确

**收尾的标志物**：能写出需求总结卡片。

## 四、需求总结卡片：拷问的交付物

### 4.1 卡片结构

对话结束时，harness-me 输出一张**需求总结卡片**：

```markdown
## 需求总结

| 维度 | 内容 |
|------|------|
| 需求概述 | 一句话 |
| 目标用户 | ... |
| 核心场景 | ... |
| 功能清单 | ... |
| 边界情况 | ...（≥3 个） |
| 非功能需求 | 性能/安全/兼容性... |
| 设计约束 | ... |
| 风险与回退 | ... |

## 验收标准（AC）

- AC-1: 当 ... 时，系统应 ...
- AC-2: ...
- AC-3: ...

## 待确认问题

- ... （拷问中未能确认的遗留问题）
```

### 4.2 卡片到 change.md 的转化

需求总结卡片是 change.md（规格真相源）的**草稿**。交接路径：

```
   拷问对话
      │
      ▼
  需求总结卡片（对话产出）
      │
      ▼
  change.md（规格真相源，.harness/changes/<id>/）
      │
      ▼
  六阶段流水线（coding → test → review → ci → verify）
```

卡片里的 AC 直接进入 change.md 的 AC 清单，成为后续所有环节的对照基准。

## 五、harness-me 与 harnessing：两个名字，一个引擎

### 5.1 关系澄清

在 Harness 体系中：

- **harnessing**：需求拷问引擎（完整技能，含问题库、决策树、输出卡）
- **harness-me**：一个极简入口——`Run a {{HARNESSING_CMD}} session.`

```
  /harness-me  （灵魂拷问的入口）
       │
       ▼
  运行 harnessing session（完整拷问引擎）
       │
       ▼
  「需求拷问引擎」对话
```

`harness-me` 的设计哲学：**它不是一个新技能，而是给"拷问引擎"一个更亲切、更容易记住的别名入口**。用户说"帮我拷问一下"的效果，和说"帮我打磨需求"一致。

### 5.2 触发场景

| 用户说 | 触发 |
|--------|------|
| "帮我理清需求" | harness-me |
| "分析这个方案" | harness-me |
| "这个设计有没有漏洞" | harness-me |
| "帮我打磨一下" | harness-me |
| "直接开始做吧" | ⚠️ 反而应该先拷问 |

### 5.3 为什么入口要轻

`harness-me/SKILL.md` 只有一行 `Run a {{HARNESSING_CMD}} session.`——这在设计上是刻意的：

1. **单一真相源**：拷问逻辑只在 harnessing 一处维护，不重复
2. **入口即别名**：用户只需要记住一个斜杠命令
3. **父技能编排**：体现"技能会调用技能"的 Harness 哲学

## 六、Go 项目中的拷问重点

### 6.1 语言相关的拷问分支

当需求涉及 Go 项目时，拷问要额外覆盖：

| 维度 | 拷问问题 |
|------|---------|
| 并发 | "这个功能会有并发访问吗？需要 goroutine 安全吗？" |
| 依赖 | "这个模块会依赖什么外部服务？接口约定是什么？" |
| 错误处理 | "出错时用户应该看到什么？错误要如何分类？" |
| 可观测性 | "需要日志/指标/追踪吗？关键字是什么？" |
| 部署 | "部署形态是什么？容器？裸机？需要优雅退出吗？" |

### 6.2 从拷问到测试策略

拷问的另一个产出是**测试策略的雏形**：

```
  "当用户输入 X 时，系统应该做什么？"
      │
      ├─▶ 正常路径：输入合法 → 正常响应
      ├─▶ 边界路径：输入为空 → 返回错误
      ├─▶ 边界路径：输入超长 → 截断或拒绝
      └─▶ 异常路径：依赖服务挂了 → 降级响应
```

每个分支都对应将来的一条测试用例。**拷问让测试"从需求里长出来"，而不是测试者事后编造。**

## 七、实战示例：一个完整拷问对话

用一个小型 Go 项目需求走一遍全流程，看看拷问如何从一句话变成可执行的规格。

### 7.1 开场：一句话需求

> 用户：我想给项目加一个"用户导出"功能。

这是典型的"一句话需求"。harness-me 的第一反应不是写代码，而是追问边界。

### 7.2 第一层拷问：需求边界

```
AI：这个功能的核心目标是什么？一句话说清楚。
用户：让运营把用户列表导出成 Excel，方便做数据分析。

AI：这个"导出"是一次性的，还是以后会反复用？
用户：以后会反复用，运营每周都要导。
→ 决策：不是一次性脚本，是正式功能 → 进 Change
```

### 7.3 第二层拷问：用户与场景

```
AI：谁是最主要的用户？他们什么时候用？
用户：运营专员，一般是月底做报表的时候。

AI：一次导出大概多少数据？要不要分页？
用户：现在五千用户左右，以后可能上万。
→ 决策：需要数据量预估，Excel 上限要确认 → 边界情况
```

### 7.4 第三层拷问：功能细节

```
AI：导出的字段有哪些？全量还是可选？
用户：全量就行，但最好能选列。

AI：导出是异步的还是同步的？数据量大时同步会超时。
用户：……没想过。那就异步吧，导出完成后通知我。
→ 决策：异步导出 + 完成通知 → 这是拷问带出的关键设计约束！
```

### 7.5 第四层拷问：设计约束

```
AI：用什么方式通知？站内信、邮件还是 Webhook？
用户：站内信就行。

AI：导出任务要不要支持取消？
用户：要，万一选错了列。
→ 决策：任务状态机（排队/运行中/完成/失败/取消）
```

### 7.6 第五层拷问：风险与回退

```
AI：如果导出到一半服务重启，任务会怎样？
用户：重新排队就行，别丢数据。
→ 决策：持久化任务状态，支持断点重试

AI：文件生成失败、磁盘满了怎么办？
用户：记日志，提示用户稍后再试。
→ 决策：错误可观测 + 用户可感知的重试入口
```

### 7.7 拷问收尾：需求总结卡片

对话结束，产出如下卡片（这是拷问的交付物）：

```markdown
## 需求总结

| 维度 | 内容 |
|------|------|
| 需求概述 | 运营可导出用户列表为 Excel（异步） |
| 目标用户 | 运营专员，月末报表场景 |
| 核心场景 | 选择列 → 提交导出 → 后台生成 → 站内信通知 |
| 功能清单 | 选列导出 / 异步任务 / 任务取消 / 完成通知 / 重试 |
| 边界情况 | 0 用户 / 上万用户 / 导出中断 / 磁盘满 |
| 非功能需求 | 导出任务持久化；失败可观测 |
| 设计约束 | 只在 Go 服务内实现，不引入外部队列 |
| 风险与回退 | 任务状态持久化，服务重启后重新排队 |

## 验收标准（AC）

- AC-1: 当运营选择字段并点击导出时，系统创建导出任务并返回任务 ID
- AC-2: 导出的 Excel 包含所选字段，无列缺失
- AC-3: 当数据量 < 1 万时，任务在 10 秒内完成
- AC-4: 当导出失败时，任务状态变为 failed 并记录原因
- AC-5: 当任务完成时，发送站内信通知运营
- AC-6: 当任务运行中时，运营可取消任务
```

### 7.8 从卡片到 Change

这张卡片直接进 `.harness/changes/<id>/change.md`（→ 第二十章 Change Management），成为后续编码、测试、评审、部署的唯一规格真相源。

## 八、拷问的心理学：为什么用户会抗拒

### 8.1 抗拒的表现

用户在拷问中常见的抗拒：

| 表现 | 含义 | 应对 |
|------|------|------|
| "随便吧" | 想快点结束 | "随便"也是最贵的决定，值得多问一句 |
| "这个不重要" | 隐藏复杂度 | 追问"它不影响结果吗？" |
| "你看着办" | 授权但推卸 | "我可以看着办，但你先告诉我最不能接受的结果是什么" |
| "需求还早" | 拖延 | 拷问不需要最终答案，只需要方向 |

### 8.2 抗拒的本质

**抗拒不是反对拷问，而是害怕暴露"我还没想清楚"。** AI 的作用是创造一个安全的空间：一次一个问题，允许"不知道"，把"没想清楚"变成"正在想清楚"。

## 九、常见反模式

### 9.1 反模式一：把拷问变成审问

```
❌ "你确定吗？" "再想想？" "真的确定？" —— 让人窒息
✅ "我们确认一下：如果 X 发生，会怎样？" —— 打开思考
```

### 9.2 反模式二：替用户补全答案

用户在犹豫时，AI 不要抢答。让沉默存在。用户补全的答案才属于用户。

### 9.3 反模式三：拷问完不产出

拷问了 20 分钟，却只留下一段对话记录。**没有总结卡片、没有 AC、没有待确认清单的拷问，等于白问。**

### 9.4 反模式四：一次拷问所有需求

一个需求拷问到满意，就够了。不要顺手把"下一个迭代的需求"也拷问了——存量太多会让规格失去焦点。

## 十、信条回顾

- **需求不是问出来的，是拷问出来的**：每个答案让一个假设显形
- **一次只问一个问题**：认知上完整，决策树上才能深入
- **不急着给答案**：拷问的目标是点燃思考，不是展示知识
- **追着信号词**："大概/应该/可能"背后是未确认的假设
- **拷问的终点是卡片**：总结卡片 + AC + 待确认清单
- **harness-me 是入口，harnessing 是引擎**：轻入口、单一真相源
- **拷问让测试从需求里长出来**：边界路径在对话中就浮现
