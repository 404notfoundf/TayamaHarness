# 关于这个跨语言 Harness 脚手架项目的学习目标与方式

专栏位置：知识星球 | 深度连接铁杆粉丝，运营高品质社群，知识变现的工具

## 一、两个核心学习目标

参与这个项目，同样我希望大家能真正带走两样硬核能力，而不是仅仅装好一套技能包、或者把 SKILL.md 读一遍。

### 1. 掌握 Harness Engineering 的落地效果与验证方法

不是背概念，而是真正理解：这个仓库交付的不是一段能独立运行的代码，而是一套**约束技能包**——`npx skills add` 装进你的项目后，它就开始约束 AI 怎么写代码。那它的「运行效果」体现在哪？在真实业务场景里：`/harnessing` 把模糊需求打磨成可测试 AC、`/coding-skill` 垂直切片实现、`/unit-test-write` 补测试、`/expert-reviewer` 双轴评审、`/unit-test-ci` 机械化门禁、`/deploy-verify` 验证线上可用——每个命令跑出来的输入/输出、在哪个环节卡住决策、质量到底守没守住，这才是 Harness 真正「运行」的地方。学会观察这些反馈，才算会验收一套约束体系。

### 2. 掌握跨语言 Harness skill 脚手架的构建能力

学会怎么把一个方法论做成**可安装、可迁移、跨语言**的 skill 产品：SKILL.md 怎么写才有效、`apply-harness` 为什么是「检测 → 参数化 → 渲染」而不是复制文件、52 个占位符怎么解耦「跨语言通用的方法论」与「语言绑定的实现」、5 种语言 × 80+ 框架的自动检测怎么做。最终能自己搭出覆盖 Java / Python / Go / Rust / Frontend 的脚手架，并在新语言新框架上迁移它。

## 二、不推荐的学习方式

❌ 直接 Clone 仓库、打开 IDE 从头读到尾、甚至读完整份 SKILL.md，然后说「我学会了」

这是这个项目最忌讳的方式，因为它是个 **skill 包而不是程序**：skill 不独立运行，它的运行效果只发生在「被装进真实项目 + 被真实命令驱动」的那一刻。只看 SKILL.md 的写法，就像只看乐谱不演奏——你知道了每个命令「怎么写的」，却完全不知道它跑起来「什么感觉」、约束「灵不灵」、流程「顺不顺」。

而且这个仓库的交付物里，真正值钱的设计决策（为什么这个方法论要跨语言通用、为什么 AC 必须先可测试、为什么阶段门禁这么设、为什么占位符这么分类）藏在每一个 SKILL.md 背后，光读是读不出来的——必须带着「跑完命令遇到的问题」回去读，才能读懂。

如果跳过实测只看源码，你拿到的只是一堆能安装的文件，而不是能迁移到下一个项目的工程化能力。

## 三、推荐的学习路径

### 第一步：安装到真实项目（快速打通）

在本地真实项目根目录执行安装，而不是在仓库里看代码：

```bash
npx skills add https://github.com/404notfoundf/TayamaHarness.git
```

安装完成后，先不急着读文件。打开 `.harness/` 目录扫一眼装进来了什么（Owner Agent、Rules、Skills、Changes、Wiki、CONTEXT.md），知道东西装齐了、命令可用了，就进入第二步。

### 第二步：实际业务场景流水线命令实操（核心收获阶段）

这是整个学习里最重要的一步——**让这套约束在真实业务里跑起来**。自己提一个真实需求（比如：给现有项目加一个 Redis 缓存层、或实现一个下单接口），然后完整走一遍流水线命令：

```
/harnessing → /coding-skill → /unit-test-write → /expert-reviewer → /unit-test-ci → /deploy-verify
```

跑的时候带着这几个问题观察每个命令的输出：

1. 需求是怎么一步步被约束成可测试 AC 的？
2. 每个命令的输入/输出是什么？阶段之间怎么衔接、怎么互相卡？
3. Harness 在哪个环节介入了决策（AC 验收、评审门禁、CI 红灯）？
4. 一次需求从 spec 到 deploy，路径如何一步步收敛到最终结果？

遇到卡点、红灯、或者觉得某个约束不合理——**记下来**，这些疑问就是第三步的入口。

### 第三步：打开 IDE 学习对应的技能（带着问题回读）

这时候才打开 IDE 读 `.harness/` 下的 SKILL.md 和源码。你已经有「跑过一遍」的感性认知，现在逐个对应第二步的问题回读写法：

- 这个命令的 SKILL.md 是怎么写的？解决什么问题、为什么这样设计、为什么那样设计不行、不变式是什么？
- `apply-harness` 怎么用参数化 + 渲染生成语言专属技能？占位符怎么分类、取舍在哪？
- 自动检测怎么从 `pom.xml` / `go.mod` 认出语言和框架？

「我的实操困惑」对「项目的设计答案」，这个对比才是进步最快的方式。

### 第四步：跟着教程从 0 推进，逐步搭建（内化成能力）

放下现成技能包，从头开始，按 `docs/` 文档中心与专栏文章的节奏，自己搭建一个 Harness + 脚手架链路。教程就在本仓库：

- **第一季·核心思想**（工程纪律即架构 / 参数化 / 自动检测 / apply-harness / SDD-TDD）——先搞懂「为什么」；
- **第二季·命令深度拆解**（40+ 个命令）——逐个拆解为什么这么设计；
- **第三季·实战与扩展**（自定义 Skill / 多Change场景上下文锁定 / 迁移实战）——把方法论迁移到新语言新框架，验证你真的懂了。

每完成一个模块，理解它的职责边界与上下游交互；逐步推进每一个 Change，观察系统如何演进、Harness 如何保持工程规范性。

## 四、最后

这个项目真正的交付物不是技能包本身，而是你跟着走完「安装 → 实操 → 回读 → 自建」整个流程之后，脑子里那张清晰的「约束—编排—验证」方法论架构图，和手里那套可复用的工程化方法论。

代码可以 Copy，能力不能。

希望大家都能沉下心来，走一遍从安装到自建的完整路径。过程可能慢，但走完回头看，值得。
