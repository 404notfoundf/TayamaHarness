# 数据库设计 — harness-db-design

> **技能标识**: `harness-db-design`
> **使用场景**: 新增/改动数据模型时——从需求卡产出表结构、索引、约束与迁移设计
> **定位**: 与 `database-migration-toolkit` 分工——本技能负责**设计**（表结构长什么样），toolkit 负责**执行**（把设计落地为可回滚的迁移脚本）

## 它做什么？

从 `.harness/changes/<id>/change.md` 的需求与验收标准，产出**数据模型设计**：实体 → 表结构 → 索引 → 约束 → 迁移脚本，并把设计沉淀到 `.harness/wiki/数据模型.md` 与迁移文件。命名须对照 `.harness/rules/数据库命名规范.md` 与 `CONTEXT.md`。

## 什么时候用？

- change 新增/修改业务实体、关联关系、状态流转、字段
- 涉及索引、唯一约束、外键、级联策略
- 需要评估存量表迁移（加字段/改类型/拆表/归档）

涉及库表的 change，宜在 **coding 之前**完成设计。

## 核心机制

### 执行流程

```
Step 1: 识别实体（从 AC 与用户故事提取名词，确定关系与基数）
    ↓
Step 2: 表结构设计（字段 / 类型 / 约束 / 命名 / ORM 映射）
    ↓
Step 3: 变更评估（对存量表：兼容性清单 + 迁移策略）
    ↓
Step 4: 落盘（更新 数据模型.md + migration-toolkit + 补充 change.md 契约影响）
```

### 设计要点

- **命名**：见 `数据库命名规范.md`（snake、`{实体}_id`、idx/uk 原样拼接、避开保留字裸名）
- **主键**：自增/雪花/UUID；禁止业务字段做主键
- **类型**：金额用定点；JSON 结构写 wiki 说明
- **索引 / 约束**：覆盖查询路径；UNIQUE/CHECK；外键按项目约定
- **软删除 / 时间**：`deleted`；`created_at` / `updated_at`（实体映射见 `ORM与库表映射.md`）

### 存量表变更评估

| 存量表 | 变更类型 | 是否破坏性 | 迁移策略 |
|--------|----------|-----------|---------|
| <表> | <变更> | 🟢 / 🔴 | <策略> |

> **铁律**：破坏性变更须先评审、可回滚，禁止直接 `DROP`。

### 目标产物

1. `.harness/wiki/数据模型.md`：erDiagram + 表结构 + 变更记录
2. 迁移脚本（推荐经 `database-migration-toolkit`），列名与 wiki 逐字一致
3. change.md「契约影响 · 数据模型」摘要

## 为什么需要它？

| 问题 | 解法 |
|------|------|
| 列名混乱（如 sku_id / sk_uid） | 命名规范 + CONTEXT + wiki 事实源 |
| 缺索引、破坏性 DROP | 设计要点 + 自检 + 迁移铁律 |
| 文档和代码脱节 | `数据模型.md` 同步更新 |

## 自检清单

- [ ] 命名符合 `数据库命名规范.md`，与 CONTEXT/wiki 一致
- [ ] 主键与索引覆盖查询路径
- [ ] 破坏性变更已标注/评审；迁移可回滚
- [ ] `数据模型.md` 已同步

## 完成标志

- 设计自检通过（含命名）
- wiki 已更新
- 迁移已交 toolkit 或脚本与 wiki 一致
